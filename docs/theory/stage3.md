# Что подтверждает резервная копия

## Логическая копия и архив

SQL-дамп MySQL/MariaDB содержит команды для восстановления объектов и данных. В PostgreSQL plain SQL читается psql, а формат custom восстанавливается pg_restore. Файл SQL Server .bak обрабатывается BACKUP/RESTORE. Расширение файла само по себе не меняет формат.

## Полная и частичная копия

Ручная копия всех предметных таблиц нужна каждому варианту. Операция по расписанию может создавать только структуру, выбранные таблицы или другой результат; такая операция не заменяет обязательную полную ручную проверку. Таблица, не включённая в частичный архив, не появится в восстановленной базе автоматически.

## Что хранится отдельно

Учётные записи сервера и параметры расписания не следует считать автоматически сохранёнными в дампе одной базы. SQL выдачи прав, параметры без паролей и инструкция запуска передаются отдельно. Сам файл копии находится вне каталога данных работающей СУБД.

## Проверка файла и проверка данных

Ненулевой размер, читаемое оглавление и SHA-256 отвечают на разные вопросы. SHA-256 позволяет сравнить байты файла; он не доказывает, что в архив включены все нужные таблицы. VERIFYONLY и --list дают сведения о копии, но не заменяют запросы к восстановленной базе.

## Отдельное восстановление

Первый опыт выполняется в _restore. Исходная база сохраняется для сравнения. Контроль включает все три таблицы, COUNT(*), SUM(id), SUM(amount) и конкретную строку. Одинаковое число строк при разных значениях не является полным совпадением данных.

## Почему важна точная копия

В журнале сохраняются имя базы, точное имя файла и время. Маска со звёздочкой может подобрать несколько файлов. Если восстановлена другая копия, даже успешная команда не подтверждает нужный опыт. В выбранном маршруте имя файла задаётся явно.
