# Роль и область прав

## Уровень разрешения

Право задаёт действие и область. Возможность создавать таблицы одной базы не означает возможность создавать учётные записи всего сервера. В этой практике начальный администратор подготавливает пользователей, admin управляет своей базой, app_user выполняет операции с данными, readonly читает.

## Особенности СУБД

В MySQL и MariaDB в имени учётной записи участвует host-часть: одинаковое имя с разными host — разные записи. Это особенность этих СУБД, а не общее правило для всех программ на Linux. GRANT на имя_базы.* ограничен этой базой; CREATE USER — отдельная серверная операция.

В PostgreSQL роль с LOGIN может входить на сервер. SUPERUSER, CREATEDB и CREATEROLE — отдельные атрибуты, а не обязательные признаки владельца одной базы. Права на схему, существующие таблицы и будущие таблицы проверяются отдельно. Правило ALTER DEFAULT PRIVILEGES относится к объектам, которые создаст указанная роль.

В SQL Server логин относится к серверу, а пользователь — к конкретной базе. Членство в db_owner не превращает SQL-логин в sysadmin. Windows-аккаунт запланированного задания и SQL-логин — также разные сущности.

## Как доказать разграничение

Для каждой роли нужен отдельный вход и проверка разрешённого действия. Только после него проверяется запрет. Иначе ошибка подключения или опечатка может быть ошибочно принята за правильный запрет. В отчёте называются операция, текущая роль, база и причина отказа.

## Видимость и доступ

Имена служебных баз и схем могут отображаться по-разному. Их видимость не равна праву изменять данные. В этой работе сравниваются конкретные полномочия и операции своей базы. Несовместимый синтаксис другой СУБД не используется как отрицательный тест.

Все точные команды находятся только в выбранном [маршруте](../practice/stage1.md). Отдельной альтернативной последовательности SQL в теории нет.
