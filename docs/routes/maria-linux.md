# MariaDB 10 · Linux

## Прежде чем копировать команды

### Работайте только в этом маршруте

ОС и СУБД должны совпадать с карточкой варианта. Здесь все команды ОС выполняются в: **терминал учебной Linux-машины**. SQL выполняется отдельно в клиенте **mariadb**. Адрес клиента на хосте и адрес внутри VM могут различаться: перепишите оба из паспорта учебной среды. Настройка сервера и канал доступа уже подготовлены; установка из другого маршрута не выполняется.

### Заполните подстановки

| В образце | В своём варианте |
| --- | --- |
| pm07_demo | pm07_vNN — имя исходной базы |
| pm07_demo_restore | pm07_vNN_restore — отдельная проверочная база |
| devices, locations, checks | Три имени таблиц из своей карточки |
| input.sql | Скачанный SQL своего варианта, сохранённый под этим рабочим именем |
| ADMIN_PASSWORD, APP_PASSWORD, READ_PASSWORD | Собственные учебные пароли, подставляемые до выполнения SQL |

В SQL сохраняйте обозначение имени таблицы: обратные кавычки вокруг имени для MySQL/MariaDB. Заменяется имя внутри них. Это важно, например, для исходной таблицы groups.

Во всех блоках SQL сначала замените длинное имя pm07_demo_restore, затем pm07_demo. Сохраняйте каждый изменённый блок в текстовом редакторе до запуска. Пароль в SQL-строке заключён в одинарные кавычки; внутреннюю одинарную кавычку удваивают. При подготовке профиля клиента учитывайте его собственное экранирование. Пароли не помещаются в снимки отчёта.

## 1. Подключение и исходные данные

### Подготовьте рабочую папку

```bash
mkdir -p "$HOME/pm07"
cd "$HOME/pm07"
pwd
```

Сохраните сюда SQL своей карточки как input.sql. Работа начинается с готовой схемы, а не с повторной разработки таблиц. Разбор использует pm07_demo; ваша сдаваемая база с самого начала называется по своему номеру.

### Войдите начальным администратором

Используйте выданную команду входа в mariadb. При парольной TCP-аутентификации пример в терминале: `mariadb -h 127.0.0.1 -P 3306 -u root -p`. Если в паспорте указан локальный socket-вход, используйте именно его. Создание базы и всех учётных записей ниже выполняется начальным администратором сервера, а не пользователем admin одной базы.

В отдельной учебной VM вход для выданных клиентов заранее ограничен подготовленным каналом. В примере имена MySQL-учётных записей имеют host-часть `%`, чтобы одна учебная роль могла пройти локальную и выданную клиентскую проверку. Эта часть — условие сопоставления клиента, а не команда настройки сетевого доступа.

```sql
SELECT VERSION(), CURRENT_USER(), DATABASE();
CREATE DATABASE pm07_demo CHARACTER SET utf8mb4;
CREATE DATABASE pm07_demo_restore CHARACTER SET utf8mb4;
CREATE USER 'admin'@'%' IDENTIFIED BY 'ADMIN_PASSWORD';
CREATE USER 'app_user'@'%' IDENTIFIED BY 'APP_PASSWORD';
CREATE USER 'readonly'@'%' IDENTIFIED BY 'READ_PASSWORD';
GRANT ALL PRIVILEGES ON pm07_demo.* TO 'admin'@'%';
GRANT ALL PRIVILEGES ON pm07_demo_restore.* TO 'admin'@'%';
GRANT SELECT,INSERT,UPDATE,DELETE ON pm07_demo.* TO 'app_user'@'%';
GRANT SELECT ON pm07_demo.* TO 'readonly'@'%';
SHOW GRANTS FOR 'admin'@'%';
SHOW GRANTS FOR 'app_user'@'%';
SHOW GRANTS FOR 'readonly'@'%';
```

### Загрузите выданный SQL от admin

Завершите соединение командой quit и войдите заново как admin в исходную базу. Полный путь к клиенту Windows берётся из паспорта. В консоли SQL выберите свою базу через USE, затем выполните SOURCE с полным путём к input.sql. На Windows путь записывается C:/Practice07/input.sql; на Linux — значение pwd и /input.sql. Это команда клиента SQL, а не строка PowerShell.

GRANT на pm07_demo.* не выдаёт глобальную привилегию CREATE USER. В этом маршруте серверные учётные записи уже созданы начальным администратором; проверка admin относится к своей базе. Дополнительный FLUSH PRIVILEGES после CREATE USER и GRANT не требуется.

### Проверьте исходный набор и графический клиент

Подключитесь к исходной базе как admin и выполните для каждой своей предметной таблицы (в примере devices):

```sql
SELECT COUNT(*) AS row_count, SUM(id) AS id_sum, SUM(amount) AS amount_sum FROM `devices`;
```

Ожидаются 4, 10, 100. Сохраните три результата с именами таблиц. access_probe содержит id=1 и value=10 и в эти три предметных результата не входит.

На хосте откройте выданный графический клиент. В DBeaver: «База данных» (Database) → «Новое соединение» (New Database Connection) → драйвер своей СУБД → «Далее» (Next); введите адрес и порт проброса **из паспорта хоста**, имя исходной базы, readonly и его пароль → «Тест соединения» (Test Connection) → «Готово» (Finish). Если отключено «Сохранять пароль», введите пароль в появившемся отдельном окне авторизации; поле пароля в основной форме при этом недоступно. Если клиент просит драйвер, используйте выданный заранее настроенный клиент; загрузка неизвестного драйвера не заменяет подготовку среды. Откройте «Редактор SQL» (SQL Editor) → «Open SQL console» (Ctrl+Alt+Enter) и выполните SELECT COUNT(*) для одной своей таблицы. Пошаговый разбор со снимками находится в [общем шаге подключения](../practice/stage1.md). В SSMS аналогично выбираются выданный сервер и SQL Server Authentication с readonly, затем New Query и своя база. Результат должен совпасть с CLI. 127.0.0.1 внутри VM и на хосте означает разные машины; порт из гостевого примера не переносится в хост автоматически.

## 2. Три отдельных подключения и права

### Позитивные опыты

Для каждого опыта создайте новое соединение и проверьте имя текущей роли. Под admin выполните создание и удаление только учебной check_admin. Под app_user измените отдельную строку access_probe и затем верните её в исходное состояние:

```sql
CREATE TABLE check_admin (id int);
DROP TABLE check_admin;
```

```sql
INSERT INTO access_probe(id,value) VALUES(9001,20);
UPDATE access_probe SET value=30 WHERE id=9001;
SELECT * FROM access_probe WHERE id=9001;
DELETE FROM access_probe WHERE id=9001;
```

Первый блок — только admin; второй — только app_user. Затем readonly читает SELECT * FROM access_probe. После опыта остаётся ровно исходная строка id=1, value=10.

### Негативные опыты

Под readonly отдельно проверьте INSERT в access_probe и DELETE строки id=1. Под app_user отдельно проверьте CREATE TABLE forbidden_app(id int). Ожидается отказ в соответствующем праве. Если действие неожиданно выполнено, зафиксируйте результат и исправьте выдачу прав из начального административного подключения; не объявляйте такую проверку успешной.

Под app_user проверьте создание серверной учётной записи командой именно этой СУБД:

```sql
CREATE USER 'forbidden_probe'@'%' IDENTIFIED BY 'Probe-Only-7Q9!23';
```

Нужен отказ в полномочиях, а не ошибка пароля, синтаксиса или уже существующего имени. Не проверяйте запрет командой другого движка. Списки системных схем не обязаны выглядеть одинаково; вывод делается по нужной операции.

## 3. Ручная копия и отдельное восстановление

### Сохраните исходные значения

После проверки прав повторите COUNT(*), SUM(id), SUM(amount) по трём таблицам и сохраните вывод как rows-before.txt. Зафиксируйте точное имя исходной базы. Первый опыт не требует повреждения этой базы.

### Сохраните дамп в точный файл

В терминале ОС вызовите mariadb-dump, подставив исходную базу. --result-file сохраняет SQL напрямую; в PowerShell не используется перенаправление >, которое в старых версиях меняет кодировку текста. Не добавляйте --databases: в учебном дампе не должно быть переключения обратно на исходное имя базы.

```text
mariadb-dump -h 127.0.0.1 -P 3306 -u admin -p --single-transaction --default-character-set=utf8mb4 --result-file=manual.sql pm07_demo
```

### Загрузите дамп только в _restore

Войдите клиентом mariadb под admin. В приглашении SQL выберите USE pm07_demo_restore; проверьте SELECT DATABASE(); и выполните SOURCE с полным точным путём к manual.sql. Звёздочки и имя файла с примерной датой здесь не используются. Исходная база при этом не очищается.

Посчитайте SHA-256: sha256sum manual.sql на Linux или Get-FileHash -LiteralPath .\manual.sql -Algorithm SHA256 на Windows. Затем выполните три контрольных запроса в _restore. Если восстанавливается не текст SQL, а архив PostgreSQL, вы выбрали другой маршрут.

### Сверьте три предметные таблицы

Запишите rows-after.txt рядом с rows-before.txt. Сопоставьте имя таблицы, количество строк, сумму id и сумму amount; проверьте также одну конкретную запись по id=1. При различии проверьте выбранный файл и его время, список таблиц, базу назначения и первое сообщение восстановления. Только после совпадения переходите к расписанию.

## 4. Операция своего варианта

### Как сохранить файлы в терминале

Из рабочей папки выполните nano config.env, вставьте блок ниже и замените NN и параметры. В nano сохраните Ctrl+O, Enter, затем Ctrl+X. Аналогично nano run.sh открывает файл каркаса. Тройные обратные кавычки оформления внутрь файлов не копируются. При переносе из Windows сохраняйте run.sh с переводами строк LF.

Создайте папку командой mkdir -p auth. Команда nano auth/client.cnf открывает нужный парольный профиль именно этого маршрута.

### Подготовьте параметры и профиль клиента

Сохраните config.env. Имена базы и пути к утилитам возьмите из своего паспорта. WORK задаёт каркас до чтения конфига; вручную запускать config.env как отдельный скрипт не требуется.

```bash
DB="pm07_vNN"
CLIENT="mariadb"
DUMP="mariadb-dump"
AUTH="$WORK/auth/client.cnf"
AS_OF="2026-11-04"
ERROR_LOG="$WORK/input-error.log"
DB_SERVICE="mariadb"
```

В auth/client.cnf сохраните текст ниже. OWN_PASSWORD заменяется своим учебным паролем, адрес и порт — значениями паспорта:

```ini
[client]
user=admin
password="OWN_PASSWORD"
host=127.0.0.1
port=3306
```

В значении password внутренняя двойная кавычка записывается как \"; обратный слеш — как \\. Кавычки вокруг всего значения сохраняются.

ERROR_LOG нужен только варианту 17: сохраните выданный в его карточке учебный журнал как input-error.log в рабочую папку. DB_SERVICE нужен только варианту 06; имя службы и право её запуска выдаются вместе со средой.

Выполните chmod 600 auth/client.cnf. Профиль не включается в репозиторий и снимки отчёта. После подстановки своей функции выполните ручной запуск каркаса из следующего шага: он использует этот профиль и должен завершиться без запроса пароля. Только после этого настраивается cron.

### Сохраните каркас run.sh

Скопируйте блок целиком. Служебные функции подключения уже соответствуют выбранной СУБД. В следующем действии заменяется только run_task.

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
umask 077
WORK="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
source "$WORK/config.env"
mkdir -p "$WORK/out" "$WORK/backups" "$WORK/logs"
LOG="$WORK/logs/run.log"
STAMP="$(date +%Y%m%d_%H%M%S)"
log() { printf '%s [%s] %s\n' "$(date -Is)" "$1" "$2" >> "$LOG"; }
trap 'rc=$?; log ERROR "exit=$rc"; exit "$rc"' ERR

db_query() {
    "$CLIENT" --defaults-file="$AUTH" --batch --raw --skip-column-names --database="$DB" --execute="$1"
}
dump_db() {
    "$DUMP" --defaults-file="$AUTH" --single-transaction --default-character-set=utf8mb4 --result-file="$1" "$DB"
}

run_task() {
    log INFO "Замените эту функцию целиком функцией своей карточки"
    return 2
}

log INFO "START db=$DB"
run_task
log INFO "END result=OK"
exit 0
```
### Ручной запуск и проверка отказа

Сохраните run.sh в рабочей папке как UTF-8 с переводами строк LF. Сначала замените функцию run_task целиком функцией своей карточки. Незаменённый каркас специально завершается ошибкой: это не выполненный вариант. Параметры находятся в config.env; пароль — в отдельном файле auth, который не включается в репозиторий.

```bash
cd "$HOME/pm07"
bash ./run.sh
printf 'exit=%s\n' "$?"
tail -n 8 logs/run.log
ls -l out backups
```

Ожидаются код 0, новая пара START/END и результат именно своей операции. Для отрицательной проверки скопируйте config.env в config-test.env и run.sh в run-test.sh; в копии скрипта замените имя подключаемого файла на config-test.env. В тестовом конфиге задайте несуществующую базу. Запустите копию: ожидаются ненулевой код и ERROR. После опыта основной run.sh и рабочий конфиг остаются исходными. Для задач, не обращающихся к БД, меняется тестовый вход операции: путь к исходному файлу или каталогу, как указано в карточке.

### Ближайший запуск cron

На учебной Linux-машине под тем же пользователем выполните crontab -e. Если редактор выбирается впервые, выберите nano. В конце добавьте две строки; в имени рабочей папки не должно быть пробелов. $HOME задаётся cron для владельца этой записи, поэтому профиль другого пользователя здесь не используется.

```cron
SHELL=/bin/bash
*/2 * * * * /bin/bash "$HOME/pm07/run.sh" >> "$HOME/pm07/logs/cron.log" 2>&1
```

В nano сохраните Ctrl+O, Enter, затем Ctrl+X. Это запуск в каждую чётную минуту, а не «ровно через две минуты». Сохраните crontab -l, запишите ближайшее подходящее время, дождитесь его и сравните новую запись в logs/run.log с результатом операции. logs/cron.log принимает только обычный вывод и ошибки; если скрипт пишет всё в run.log, cron.log может остаться пустым. Тип журнала указан в паспорте. Для systemd выполните journalctl -u cron --since "10 minutes ago" (либо выданное имя crond). Для выданного текстового /var/log/syslog выполните grep CRON /var/log/syslog | tail -n 10. Найдите CMD со своим run.sh и назначенным временем. Доступ к этому журналу должен быть выдан заранее; отсутствие файла syslog не доказывает отсутствие запуска.

Для варианта 06 требуется учётная запись ОС, которой на выделенной VM разрешён запуск нужной службы. Её выдаёт преподаватель до проверки; остальные варианты используют выданную обычную учётную запись. Рабочая папка и профиль клиента принадлежат фактическому владельцу задания.

### Постоянная периодичность

После проверочного запуска замените тестовую строку единственной постоянной. Ежедневный запуск: 0 3 * * *; еженедельный: 0 3 * * 1; ежечасный: 0 * * * *. Остальная часть команды остаётся прежней. При отсутствии частоты в карточке выберите её и объясните. Сохраните окончательный crontab -l; две параллельные записи для одного скрипта не нужны.

## Итог выбранного маршрута

В своей карточке найдите функцию операции и её обязательный опыт. Выполните только её, добавьте выбранное индивидуальное дополнение, затем заполните журнал: подключение, права, ручная копия, отдельное восстановление, ручной запуск, контролируемый отказ и действительный запуск планировщика.

Сдаваемая инструкция своего репозитория позволяет повторить запуск с выданными параметрами без пересоздания производственной модели и без чтения другого маршрута. Снимки и результаты отчёта принадлежат своей работе; приведённые ожидаемые значения не заменяют наблюдения.
