    Этап 3. Резервное копирование и восстановление¶

    Зачем нужны бэкапы¶

    База данных может пострадать в нескольких ситуациях:

    • человек ошибся: выполнил DELETE или DROP TABLE без WHERE;
    • сбой питания или жёсткого диска;
    • ошибочное обновление сервера сломало структуру;
    • вирус или вымогательское ПО зашифровало файлы.

    Во всех четырёх случаях единственное, что спасает данные, — это актуальная резервная копия и понимание, как из неё восстановить базу.

    Учебное правило: бэкап считается рабочим только после успешного восстановления. Просто сделать файл недостаточно — его нужно один раз восстановить.

    Виды резервных копий¶

    Признак Виды
    По способу хранения Логический (SQL-скрипт) и физический (копия файлов)
    По полноте Полный, дифференциальный, инкрементальный
    По состоянию сервера Горячий (сервер работает), холодный (сервер остановлен)
    По времени восстановления На момент бэкапа; на любой момент (point-in-time recovery)

    В учебной практике достаточно логического полного бэкапа в горячем режиме — этого хватает для всех тренировочных задач.

    Логический и физический бэкап¶

    Признак Логический (mysqldump, pg_dump, BACKUP DATABASE) Физический (копия data каталога, xtrabackup)
    Содержимое SQL-команды (CREATE TABLE, INSERT) Бинарные файлы данных
    Размер Больше Меньше
    Скорость снятия Медленнее Быстрее
    Скорость восстановления Медленнее Быстрее
    Переносимость между версиями Высокая Низкая
    Подходит для учебной практики Да Не нужно

    Логический бэкап — это текстовый файл, который можно открыть редактором, увидеть структуру, при необходимости отредактировать или восстановить выборочно.

    MySQL/MariaDB: mysqldump¶

    Полный бэкап одной БД:

    mysqldump -u admin -p \
    --single-transaction \
    --routines --triggers --events \
    library > library_2026-05-25.sql

    Полный бэкап всех БД:

    mysqldump -u admin -p --all-databases > all_2026-05-25.sql

    Только структура без данных:

    mysqldump -u admin -p --no-data library > library_schema.sql
    Опция Назначение
    --single-transaction Снимок без блокировки таблиц (для InnoDB)
    --routines Включить хранимые процедуры
    --triggers Включить триггеры
    --events Включить события планировщика
    --no-data Только структура
    --databases Включить CREATE DATABASE в дамп
    --quick Не загружать всю таблицу в память

    PostgreSQL: pg_dump и pg_restore¶

    Текстовый дамп:

    pg_dump -h 127.0.0.1 -U admin -d library -F p -f library_2026-05-25.sql

    Сжатый бинарный архив (рекомендуется):

    pg_dump -h 127.0.0.1 -U admin -d library -F c -f library_2026-05-25.dump

    Бэкап всех баз сразу:

    pg_dumpall -h 127.0.0.1 -U postgres -f all_2026-05-25.sql

    Просмотр содержимого custom-архива:

    pg_restore -l library_2026-05-25.dump | head
    Формат -F Что это
    p (plain) Текстовый SQL
    c (custom) Сжатый бинарный архив с метаданными
    t (tar) Архив tar
    d (directory) Папка с файлами по таблицам

    MS SQL Server: BACKUP DATABASE¶

    В T-SQL:

    BACKUP DATABASE Library
TO DISK = N'D:\Backups\Library_2026-05-25.bak'
WITH FORMAT, INIT, COMPRESSION, NAME = N'Library full backup';

    Через PowerShell:

    Invoke-Sqlcmd -ServerInstance ".\SQLEXPRESS" -Query @"
BACKUP DATABASE Library
TO DISK = 'D:\Backups\Library_2026-05-25.bak'
WITH INIT, COMPRESSION;
"@

    Восстановление: MySQL/MariaDB¶

    # Полное восстановление БД из текстового дампа
mysql -u admin -p library < library_2026-05-25.sql

# Если в дампе есть CREATE DATABASE
mysql -u admin -p < library_2026-05-25.sql

    Порядок действий при «случайном удалении»:

    1. Сохранить текущее состояние (отдельный бэкап «до восстановления»).
    2. Создать новую пустую БД с другим именем (например, library_restore).
    3. Применить дамп в эту БД.
    4. Сверить количество строк до и после.
    5. Перенести нужные данные INSERT … SELECT в рабочую БД, либо переименовать БД целиком.

    Восстановление: PostgreSQL¶

    Из текстового дампа:

    psql -h 127.0.0.1 -U admin -d library_restore -f library_2026-05-25.sql

    Из custom-архива:

    pg_restore -h 127.0.0.1 -U admin -d library_restore \
    --clean --if-exists library_2026-05-25.dump
    Опция pg_restore Назначение
    --clean Удалять объекты перед восстановлением
    --if-exists Не падать, если объекта не было
    --list Показать содержимое архива
    -j 4 Параллельное восстановление в 4 потока

    Восстановление: MS SQL Server¶

    USE master;
ALTER DATABASE Library SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

RESTORE DATABASE Library
FROM DISK = N'D:\Backups\Library_2026-05-25.bak'
WITH REPLACE, RECOVERY;

ALTER DATABASE Library SET MULTI_USER;

    SINGLE_USER нужен, чтобы никакие сессии не держали БД и восстановление прошло без ошибок.

    Проверка целостности бэкапа¶

    СУБД Команда
    MySQL head -50 library.sql и grep -c "INSERT INTO" library.sql
    PostgreSQL (custom) pg_restore --list library.dump
    MS SQL RESTORE VERIFYONLY FROM DISK = 'D:\Backups\Library.bak'

    Дополнительно вычисляется контрольная сумма файла, чтобы убедиться, что он не повреждён при копировании:

    sha256sum library_2026-05-25.sql > library_2026-05-25.sql.sha256
sha256sum -c library_2026-05-25.sql.sha256

    В PowerShell:

    Get-FileHash D:\Backups\Library_2026-05-25.bak -Algorithm SHA256

    Где хранить бэкапы¶

    Учебное правило: не там же, где база.

    Источник риска Что произойдёт, если бэкап рядом
    Удалили БД и каталог Удалится и бэкап
    Зашифровал вирус Зашифрует и бэкап
    Отказ диска Потеря и базы, и бэкапа

    Минимально приемлемое расположение: отдельная папка на другом диске, на сетевой шаре или вне виртуальной машины. В учебной практике достаточно отдельной папки ~/backups/ с правом записи только администратора.

    Жизненный цикл одного бэкапа¶

    flowchart LR
    A[Снять бэкап] --> B[Сохранить контрольную сумму]
    B --> C[Перенести вне сервера БД]
    C --> D[Проверить чтение архивом / VERIFYONLY]
    D --> E[Тестово восстановить в отдельную БД]
    E --> F[Записать в журнал администратора]

    Если на шаге D или E возникает ошибка, бэкап считается испорченным и должен быть удалён.

    Расписание¶

    Учебная практика на этом этапе делает бэкап руками. Автоматизация расписания — содержание этапа 4.

    Журнал восстановления¶

    Любое восстановление обязательно фиксируется. Минимальный формат:

    2026-05-25 14:30:00 | RESTORE | библиотека | библиотечный сервер
Источник: backup_2026-05-24_22-00-00.sql.gz
Целевая БД: library_restore
Команда: mysql -u admin -p library_restore < backup_2026-05-24.sql
Результат: успешно; 5 таблиц; 1248 строк; время 41 секунда
SHA-256 источника: a7f8...c2c4 (совпадает с эталоном)

    Артефакты этапа¶

    К концу этапа собираются:

    • файл бэкапа в указанном формате (.sql / .dump / .bak);
    • файл контрольной суммы рядом;
    • скриншот вывода head / pg_restore --list / RESTORE VERIFYONLY;
    • описание сценария «удалили таблицу — восстановили»: что делали, как сверяли результат;
    • журнал восстановления в текстовом виде.
